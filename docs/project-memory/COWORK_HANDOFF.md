## 2026-07-25 update (round 2: IM question-variety systemic bug + BODMAS no-wrap + chip color): 3 more live-found bugs, all root-caused, fixed, tested, delivered, and LIVE-VERIFIED

**tl;dr:** Straight after round 1 (PR #394, below) went live, Shailesh looked at it and found 3 more issues, with an explicit standing instruction this round: "first go through everything and then come back to me with the last fuckin findings, i do not have time to go on waste it on a single fuckin issue" — investigate everything up front, report once, not one bug at a time. All 3 root-caused, fixed, tested, and live-verified against production with a fresh test blueprint after Shailesh's follow-up "fixes are live go verify everything end to end and make sure they are working."

1. **BODMAS questions must never wrap — always a single line, exactly matching the mock-exam convention**, not just "allow wrap instead of overlap" (round 1's stopgap fix, now superseded). Root cause: the Assessment Studio's question preview always rendered the question/answer grid in a narrow ~360px column regardless of question type. The mock exam preview (`mock-studio/[mockId]/page.tsx`) already solves this exact problem via a `needsWideQuestionLayout()` pattern — switching to a full-width single-column grid for `EXPRESSION_WORKSHEET`/`FINANCIAL_TABLE` display types — but the assessment preview never had the equivalent switch. Fixed in `frontend/app/admin/assessment-blueprints/page.tsx`'s `GeneratedQuestionPreview` by copying the identical conditional (checks `displayType`/`display_type` on the question, already correctly persisted by `app/question_engine/im/generator.py` at generation time, so no extra resolution logic was needed on the frontend side unlike mocks, which infer it live).
2. **Multiplication/division only ever generated 2D×2D and 4D/2D, never any of the level's other real digit patterns** — the biggest and most consequential find of the whole day. Root cause, in `backend/app/services/assessment_engine_service.py`'s `ImSectionRegistryConfig()`: every `ConceptSpec` a section's concept-pool entry carries — `multiplicationDigits`, `divisionDigits`, `isLongDivisionEstimation`, `answerPositionDirection`, `positionRange`, `hasSquareTerm`, `bodmasTemplate`, `borrowingMode`, `isDecimal`, `decimalPlaces`, `explicitDigitCount`, `rowCount`, `magnitudeMin/Max`, `fixedTimes`, `addRange`, `skillStackerLinear`, and more — was being discarded except for `conceptFamily`/`title` before being handed to the question generator, so every question for a given concept family silently fell back to `operands.py`'s hardcoded default regardless of which curriculum variant the level actually called for. This wasn't scoped to multiplication/division or to IM-L4 — it affected every IM level and every concept family with more than one pool variant, and as a direct consequence **`answerPositionDirection: "FIND_POSITION"` could never be reached, so "Find the Position of the First Natural Number" questions could never generate at all.** Fixed by merging every `ConceptSpec` field except `conceptFamily`/`title` straight into `GeneratorConfig`, mirroring the pattern MM's equivalent config-builder already uses correctly. Added a new regression test, `test_im_assessment_generation_varies_digit_patterns_and_division_digit_pairs` / position-direction assertions in `backend/tests/test_section_wise_assessment_generation.py`, which generates a real IM-L4 assessment across an 8-section distribution satisfying the 100-marks invariant and asserts real variety in multiplication/division digit pairs and both position directions appearing. 48/48 backend tests pass (47 existing + 1 new), no regressions.
3. **Section-name chip didn't match the section-number chip's blue styling** for IM (and every module except MM) — plain gray instead. Fixed by removing the module-based conditional in `GeneratedQuestionPreview` so both chips unconditionally share `rounded-full math-admin-studio-chip px-3 py-1 text-xs font-black`. (Flagged, not touched: the identical pattern exists in the mock studio's own per-question chips — Shailesh only flagged the assessment view this round, so that one's left as a known, separate item if he wants it later.)

## 2026-07-19 update (round 2): live-verifying round 1's own fix surfaced a second, real, unrelated bug in MM/IM assessment generation — root-caused, fixed, delivered as PR #347 (`131a44a`), and confirmed live end to end

**tl;dr:** Asked to verify round 1's work live via Claude-in-Chrome against production. YLM gate and the deploy itself both confirmed live and correct. Trying to live-verify the MM decimal-crash fix (build a real MM-L1 full-level assessment, generate a preview) failed — but not with the crash that was fixed. A different, genuinely pre-existing bug blocked generation entirely, on Lesson 1, before execution ever reaches the code path round 1 touched.

**The bug:** generating any MM-L1 full-level assessment preview failed with `ASSESSMENT_QUESTION_GENERATION_FAILED`: `"Master Module generator produced invalid question 1 for WHOLE_NUMBER_MULTIPLICATION"`. Root-caused with a script rather than guessed (captured the real API error via XHR-patching in the browser console, then reproduced offline): `DPSSection.generator_config_json` stores the real per-section definition — including `multiplicationDigits`/`divisionDigits` — nested one level deeper than expected, under an `"activeSection"` key. Both `seed_master_module.py` and `seed_intermediate_module.py`'s `_upsert_sections()` build it that way (`{**config, "activeSection": section_definition}`), because that's the shape the section-locked competition-mock/DPS-practice generation path expects and correctly unpacks (`GenerateMmQuestionSet`'s curriculum-map branch spreads `**Section` — the real dict, including `multiplicationDigits` — directly onto its `GeneratorConfig`). But the assessment-generation path's `MmSectionConfig()`/`ImSectionConfig()` (`assessment_engine_service.py`) were reading `Section.generator_config_json` flat, so `multiplicationDigits`/`divisionDigits` were invisible to `_MultiplicationDigits()`/`_DivisionDigits()` (`mm/operands.py`) on this path only.

**Why it manifests as a permanent, deterministic failure (not flaky):** without `multiplicationDigits` visible, the generator falls back to a difficulty-stage default — question 1 of any section is `DifficultyStage(0)` = `WARM_UP`, which the generator maps to a 2D×1D shape. **The design landed on, and what's now built:**

Deliberately keyed on the activity's **allotted** `duration_seconds` (fixed, admin-configured, correct from the moment an attempt starts), not `time_taken_seconds` (derived after submission, and exactly the field with the timing bug found in this audit). ## 2026-07-11 update (round 2): heatmap ghost-bar CSS bug + dynamic pace weighting + info icon — prepared, not yet delivered

Round 1 (below) shipped to main as PR #303 and was confirmed live by the developer via screenshots: tooltip data now correctly showed the two real mock exam completions (accuracy/time matched production records exactly), proving the multi-source data-pooling fix works. But the live screenshots also surfaced two things nobody had caught yet:

1. **Ghost bars.** The tooltip showed correct data on hover, but no visible colored bar rendered underneath it — a "ghost plot." Root cause: the heatmap row (`frontend/app/student/dashboard/page.tsx`) uses `items-end` on its flex container, which stops each day-column from stretching to the row's fixed height — each column's own height became auto/content-based instead. The bar inside is styled with `height: {percentage}%`, and a CSS percentage height cannot resolve against an auto-height parent, so it silently computed to zero. Pre-existing bug, not introduced by round 1 (round 1 never touched this render block) — this is very likely the exact thing `OPEN_ISSUES.md`'s long-standing "browser-QA the heatmap tooltip stack" item was warning about, just never confirmed until today. Fixed by giving each bar an explicit-height track (`h-20`) to size against, instead of an ambiguous auto-height parent.

2. **Tier didn't match intuition: 97% accuracy scored a lower tier than 92%.** Not a bug — a formula design issue, confirmed by the numbers: the pre-existing `flowState` formula (`accuracy × 0.7 + min(speed × 6, 30)`) uses a flat "5 questions/minute" threshold for the speed bonus. The 97%-accuracy day was a 60-minute mock exam (~1.7 q/min → small bonus); the 92%-accuracy day was a 30-minute mock of similar size (~3.3 q/min → much bigger bonus) — enough to flip the ranking. Discussed the tradeoff with the developer directly: speed is intentionally a major factor in this abacus program (not something to water down), but it needs to be judged relative to what each specific task was designed to take, not one flat number applied to a 5-minute drill and an hour-long exam alike. Resolution: score pace per attempt as `expectedDurationSeconds ÷ actualTimeTakenSeconds` (capped at 1.5×), averaged across a day's attempts, feeding the same ~30-point ceiling the speed bonus always had — the weighting balance is unchanged, only what "fast" is measured against changed.

## 2026-07-10 update: first real dry run caught two genuine Windows bugs

Ran the actual pipeline (qa-reviewer → sre-devops) on this session's own uncommitted rework via local Claude Code, exactly as planned. qa-reviewer correctly returned FAIL and blocked delivery — both bugs were real, both were artifacts of writing/testing these scripts in the Cowork Linux sandbox without accounting for Windows execution:

1. `.agents/rollback.py:74` — `git rm -rf --ignore-unmatch . > /dev/null` under `shell=True` on Windows runs through cmd.exe, not bash; `/dev/null` isn't a Windows path and was creating a stray `C:\dev\null` file instead of discarding output. Fixed: replaced with plain ASCII (`WARNING:`, `FAILED:`, `-`) in both files. Verified via a full non-ASCII scan of every `print()` line in both scripts — clean.

Both fixes applied directly from Cowork (same mounted repo), verified with `python -m py_compile`, not yet re-reviewed by qa-reviewer or delivered.
